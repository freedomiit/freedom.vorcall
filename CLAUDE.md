# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Vorcall: a private chat for a friend group, invite-only accounts, one server whose text and voice channels sit under categories, plus two-person DMs. Membership is not something to join or leave: every account belongs to the server, and a channel is visible exactly when `VIEW_CHANNEL` resolves for that member. Roles (colour, icon, position, hoist) carry 21 granular permissions, overridable per channel and per member; members have profiles (avatar, banner, nickname, description, accent colour); the owner bypasses every check. Moderation covers kick, ban (with message tombstoning), server mute/deafen, move and priority speaker. Every voice channel and every DM has a voice session (push-to-talk or voice activation, with echo cancellation and noise suppression on the microphone, over a UDP media relay) and screen sharing. Native Rust desktop client (iced), ASP.NET Core (.NET 10) backend, protobuf frames over a single WebSocket. MVP scope only — see `README.md` for what exists and what deliberately doesn't.

## Structure

- `proto/vorcall.proto` — shared schema. Both sides generate code from it at build time.
- `PROTOCOL.md` — wire framing, connection/session state machines, permission resolution, limits. Read it before touching `server/Chat/`, `server/Permissions/` or `client/crates/vorcall-core/`. Read `PROTOCOL.md` § Voice before touching `server/Voice/`, `client/crates/vorcall-voice/` or the voice parts of `ConnectionRegistry.cs`; read § Screen share and § Media transport there too before touching any of the screen-share paths in those same files, plus `client/crates/vorcall-screen/` and `client/crates/vorcall-app/src/{workers/share.rs,view/stage.rs}`.
- `server/` — ASP.NET Core backend, `Vorcall.Server.csproj`. `server/Dockerfile` builds with the **repository root** as context (it needs `proto/`). `server/Auth/` — accounts, tokens, `InviteService` (create/list/revoke, shared by the CLI and the REST endpoints) and `RefreshTokenSweeper` (deletes refresh-token rows 7 days after expiry or revocation). `server/Api/` — REST endpoints: `MessagesEndpoints.cs`, `AttachmentsEndpoints.cs`, `ImagesEndpoints.cs`, `InvitesEndpoints.cs`, `BansEndpoints.cs`, `UsersEndpoints.cs`, `AuthEndpoints.cs`, `UpdatesEndpoints.cs`, `DiagnosticsEndpoints.cs`, `MetricsEndpoints.cs`, `AdminEndpoints.cs`, plus `PrivateSource.cs` (who may reach `/metrics` and `/api/admin/*`). `server/Cli/` — the `invites`/`users`/`server` admin subcommands. `server/ServiceSetup.cs` — DI/middleware wiring.
- `server/Permissions/` — the pure permission engine: `Perm` (the bit enum) and `PermNames` (the wire names, both in `Perm.cs`), `Perms` (`All`, `ServerScoped`, `ChannelScoped`, `EveryoneDefault`, `Clean`, `Has`), `Defs.cs` (`RoleDef`/`OverrideDef`/`ChannelDef`/`MemberDef`), `PermissionEngine` (`Resolve`, `HighestPosition`, `CanManageRole`, `MissingGrant`, `CanTarget`, `InsertPosition`, the write-time checks). Nothing in it touches the database or the wire.
- `server/Chat/` — `ConnectionRegistry.cs` (the in-memory mirror of the whole server under one gate: members with their roles and a per-online-member `Visible` set, channels with their overrides and voice slots, roles with a cached hierarchy; `LoadAsync`, `AttachAsync` = the Hello sequence, `Resolve`/`Has`/`CanView`, the fan-out primitives, voice and screen-share signalling) and `ConnectionRegistry.Management.cs` (the same partial class: every management and moderation operation — check, persist, mirror, broadcast — each returning an `OpResult` the handler maps onto an error code). Persistence lives in the directories: `ChannelDirectory` (channels, categories, overrides, DMs, read cursors and the unread/mention counters), `RoleDirectory`, `MemberDirectory` (profiles, nicknames, bans with the tombstoning transaction, kicks), `ServerDirectory` (the single `server` row, seeding, owner). Plus `ChatSocketHandler` (every frame), `ClientConnection`, `MessageService`, `WriteLimiter` (the per-account write-frame bucket), `Names` (the 32/256-scalar name grammar), `Validation` (channel-id parsing, text normalisation, `@everyone`/`@here` detection), `Mentions` (`<@id>` token extraction).
- `server/Voice/` — the voice relay: `VoiceOptions` (config, incl. `ShareEnabled`/`ShareMaxKbps`/`MaxSharersPerRoom`), `VoiceRelay` (the UDP hosted service; also fans video and share audio out to a sharer's watchers, forwards keyframe requests, drops a server-muted session's audio and skips deafened recipients), `VoiceSession`, `MediaHeader`, `ReplayWindow`, `TokenBucket`.
- `server/Attachments/` — `AttachmentsOptions` (config), `AttachmentStore` (streaming upload/download, on-disk paths), `ImageStore` (avatars, banners, the server icon, role icons — a separate store with a purpose per row, files under `<AttachmentsDir>/images/`), `AttachmentSweeper` (the unlinked-upload sweep and the unreferenced-image sweep).
- `server/Logging/` — `LoggingOptions` (`Vorcall:LogsDir`), `LoggingSetup` (Serilog: console + daily compact-JSON files, wired only from `Program.cs`). `server/Metrics/` — `ServerMetrics` (the counters `/metrics` renders; `server/Api/MetricsEndpoints.cs` writes the Prometheus text by hand). `server/Diagnostics/` — `DiagnosticsOptions`, `DiagnosticsSetup`, `DiagnosticsStore`, `DiagnosticsSweeper` (client problem reports under `Vorcall:DiagnosticsDir`, 30-day retention; `server/Api/DiagnosticsEndpoints.cs` is the upload). `server/Admin/` — `AdminOptions` (`Vorcall:AdminKey`/`AdminUrl`), `AdminSetup`, `DisabledAccounts` (the 30 s cache of the `users.disabled_at` lock, which is **not** a ban).
- `server/Data/` — the entities (`Server`, `Category`, `Channel`, `ChannelRead`, `ChannelOverride`, `Role`, `MemberRole`, `Ban`, `Image`, `User`, `Message`, `Attachment`, `Reaction`, `Invite`, `RefreshToken`), `AppDbContext`, and `Seed.cs` (`EnsureSeededAsync`: the `server` row, `@everyone`, the category "General" holding the text channel `general` and a voice channel `General`).
- `tests/Vorcall.Server.Tests/` — the xunit suite for the server: the pure unit tests (the permission-engine matrix, the name grammar, validation) plus the integration suite that boots the backend in-process (`Infrastructure/`: `VorcallFactory` over `WebApplicationFactory`, `ServerFixture`/`ServerCollection`, `WsClient`, `Party`, `Accounts`, `Frames`, `Proto`, `Uploads`, `Releases`, `Png`, `History`, `Names`) against the compose Postgres, in a per-run `vorcall_test_<hex>` database, speaking the protocol with the server's own generated protobuf types. It lives **outside** `server/` on purpose: the SDK's default compile glob would otherwise pull the test files into `Vorcall.Server.csproj`. Run it with `dotnet test tests/Vorcall.Server.Tests`. It is the primary runtime oracle for the chat and REST surface; voice and share media keep `vorcall-probe`.
- `client/` — Cargo workspace: `crates/vorcall-proto` (generated protobuf code), `crates/vorcall-core` (connection/protocol logic: `auth.rs`, `session.rs`, `http.rs` (with the shared `get_bytes`/`post_proto`), `endpoints.rs`, `permissions.rs` (the bit-for-bit mirror of `server/Permissions/`), `attachments.rs`, `images.rs` (image upload/download), `admin.rs` (invites, bans and member lists over REST), `history.rs`, `mentions.rs`, `config.rs`, `connection.rs` (the reconnecting loop, `Command`/`Event`, share/watch and admin commands), `diagnostics.rs` (the rolling `vorcall.log` next to `config.toml`, the panic hook and `crash-<utc>.txt`), `report.rs` (uploads them to `POST /api/diagnostics`), and `src/update/` — the updater: `version.rs`, `keys.rs`, `manifest.rs`, `hash.rs`, `client.rs`, `swap.rs`, `pending.rs`), `crates/vorcall-voice` (the media engine: packet framing, AEAD, Opus, jitter buffer, UDP engine, `video.rs` (video fragmentation/reassembly and keyframe gating), stereo share-audio codec types and stereo `Playout`, and `cleanup.rs`, the `aec3` echo-cancellation/noise-suppression/auto-gain chain plus `ShareCleanup` (echo cancellation only, for loopback share audio) — no cpal/rodio/iced, so it builds and tests without an audio device or a GUI), `crates/vorcall-screen` (screen capture and the video codec, no iced/rodio/cpal on the crate's own account: `preset.rs` (resolution/fps/bitrate table), `codec.rs` (OpenH264 encode/decode built from vendored C++ via `cc`, no cmake), `scale.rs`, `pattern.rs` (the probe's test pattern), and per-platform capture backends under `windows/`, `macos/` and `linux/`), `crates/vorcall-hotkey` (a system-wide input listener for several bindings at once — push-to-talk, toggle mute, toggle deafen: `Listener::start(Vec<(ActionId, Binding)>, ..)` with `Binding { trigger, ctrl, shift, alt }`; per-platform backends for Windows/macOS/Linux X11/Wayland, with a window-focused fallback when global capture is unavailable), `crates/vorcall-probe` (headless voice probe binary, `vorcall-probe`; the runtime oracle for the voice path — see README § Voice; also carries the `check-update`/`apply-update` subcommands, the runtime oracle for the updater, the `--share-seconds`/`--watch` share/watch oracle, and `capture.rs`, the `--capture-seconds` capture-only oracle that needs no server), `crates/vorcall-release` (release-side tool, binary `vorcall-release`: `gen-key`/`manifest`/`sign`/`verify`, driven by `.github/workflows/release.yml`), `crates/vorcall-app` (iced GUI, binary `vorcall`).

- `server/Updates/` (`UpdatesOptions`, `UpdateManifestStore`) and `server/Api/UpdatesEndpoints.cs` — serve the signed manifest and the release assets under `/api/updates/*`.

## Commands

Local dev:

```
docker compose up -d db
~/.dotnet/dotnet run --project server/Vorcall.Server.csproj      # http://localhost:5000
cd client && VORCALL_SERVER_URL=http://localhost:5000 cargo run -p vorcall-app
```

Admin CLI (invites, users, server — see `README.md` § Admin CLI):

```
~/.dotnet/dotnet run --project server/Vorcall.Server.csproj -- invites new
~/.dotnet/dotnet run --project server/Vorcall.Server.csproj -- server show
~/.dotnet/dotnet run --project server/Vorcall.Server.csproj -- server set-owner alice
```

Regenerate the UI icons (this mode needs no shapely, unlike the brand outputs; every SVG must come out byte-identical):

```
python3 assets/brand/gen.py icons assets/icons
```

Server test suite — the primary runtime oracle for the chat/REST surface (accounts, channels and DMs, rich messages, attachments, share signalling, rate limits, admin, plus the pure unit tests); needs the compose Postgres, creates and drops a `vorcall_test_<hex>` database per run; `VORCALL_TEST_ADMIN` overrides the admin connection string, default `Host=localhost;Port=5433;Username=vorcall;Password=vorcall;Database=postgres`:

```
docker compose up -d db && ~/.dotnet/dotnet test tests/Vorcall.Server.Tests
```

Smoke suite — a second opinion on the wire protocol, living outside the repo at `~/.cache/vorcall-smoke` (regenerate `vorcall_pb2.py` with grpcio-tools after any proto change; it seeds rows into the local DB; it is voice-aware — it skips voice frames unless a step expects them; it covers channels and categories, DMs, rich messages (reply/edit/delete/reactions), attachments and images, roles and overrides, kick/ban, voice moderation and the invites/bans REST endpoints):

```
uvx --with websockets --with protobuf python ~/.cache/vorcall-smoke/smoke.py full --http http://localhost:5000 --ws ws://localhost:5000/ws --key dev --invites A,B,C
```

Voice probe (two terminals; the runtime oracle for the voice path — see README § Voice for the full recipe, exit codes and JSON fields). With neither `--channel <id>` nor `--channel-name <name>` it joins the voice channel named `General`:

```
cd client && cargo build -p vorcall-probe
VORCALL_SERVER_URL=http://localhost:5000 VORCALL_PROBE_PASSWORD=... ./target/debug/vorcall-probe --username alice --send-seconds 10 --listen-seconds 14 --expect-peer
VORCALL_SERVER_URL=http://localhost:5000 VORCALL_PROBE_PASSWORD=... ./target/debug/vorcall-probe --username bob --send-seconds 10 --listen-seconds 14 --expect-peer --tone-hz 660
```

Voice-activation oracle: one probe proves the gate holds silence back; two probes prove the gate lets a tone through.

```
VORCALL_SERVER_URL=http://localhost:5000 VORCALL_PROBE_PASSWORD=... ./target/debug/vorcall-probe --username alice --send-seconds 4 --listen-seconds 5 --vad --tone-amplitude 0 --expect-silence
VORCALL_SERVER_URL=http://localhost:5000 VORCALL_PROBE_PASSWORD=... ./target/debug/vorcall-probe --username alice --send-seconds 10 --listen-seconds 14 --vad --tone-amplitude 0.3 --expect-peer
VORCALL_SERVER_URL=http://localhost:5000 VORCALL_PROBE_PASSWORD=... ./target/debug/vorcall-probe --username bob --send-seconds 10 --listen-seconds 14 --vad --tone-amplitude 0.3 --expect-peer --tone-hz 660
```

Screen share probe (two terminals; the runtime oracle for the share path — see README § Screen share for the full recipe, exit codes and JSON fields):

```
cd client && cargo build -p vorcall-probe
VORCALL_SERVER_URL=http://localhost:5000 VORCALL_PROBE_PASSWORD=... ./target/debug/vorcall-probe --username alice --share-seconds 10 --share-audio --listen-seconds 14
VORCALL_SERVER_URL=http://localhost:5000 VORCALL_PROBE_PASSWORD=... ./target/debug/vorcall-probe --username bob --watch alice --expect-video --expect-share-audio --listen-seconds 14
./target/debug/vorcall-probe --capture-seconds 5 --capture-audio
```

`--capture-seconds` needs no server: it opens the portal picker on Linux and runs ScreenCaptureKit on macOS; exit 0 = capture ran and the stop path completed. The sharing probe's `"share"` JSON carries `send_failures` (fragments the socket refused for good). A macOS build of the probe comes out of every `release.yml` run as the workflow artifact `vorcall-probe-macos-aarch64` — see README § Screen share for the owner's recipe on a Mac.

Update oracle (runtime oracle for the updater, against a local server; needs an existing account):

```
VORCALL_PROBE_USER=alice VORCALL_PROBE_PASSWORD=... scripts/update-oracle.sh --http http://localhost:5000
```

`vorcall --version` prints `vorcall <version> <platform>` and exits before endpoint resolution and iced ever start — the release workflow uses it to check a build against the tag.

Gates (must pass before considering a change done):

```
cd client && cargo fmt --all --check && cargo clippy --all-targets -- -D warnings && cargo build && cargo test -p vorcall-voice -p vorcall-core -p vorcall-release -p vorcall-app -p vorcall-hotkey -p vorcall-screen
dotnet build server/Vorcall.Server.csproj -warnaserror
docker compose up -d db && dotnet test tests/Vorcall.Server.Tests
```

Automated tests are the six crates' unit tests and `tests/Vorcall.Server.Tests` (the server suite above, whose integration tests need the compose Postgres); the voice and share media paths have no automated test — `vorcall-probe` is their oracle, and the Python smoke suite is a second opinion on the wire protocol. `cargo xwin clippy --target x86_64-pc-windows-msvc -p vorcall-screen` (from `client/`) is the only check available for the Windows capture backend on this machine; the macOS backend compiles only on `release.yml`'s macOS runner (a dry-run dispatch, no tag needed).

## Gotchas

- **The `ChannelsRolesProfiles` migration is one-way.** It rewrites every room into a category plus a text and a voice channel, converts DMs and read cursors onto numeric channel ids, and drops `rooms`/`room_members`; `Down()` throws. `pg_dump` production before the deploy that carries it — restoring that dump is the only rollback.
- **`general` is identified by `server.general_channel_id`, never by name.** Channel names are not unique, so a channel called `general` is not necessarily *the* general channel. It cannot be deleted, and `VIEW_CHANNEL` on it cannot be denied to `@everyone` (refused at write time **and** forced on in resolution).
- **The permission mirror in `client/crates/vorcall-core/src/permissions.rs` must match `server/Permissions/PermissionEngine.cs` bit for bit**, and both are tested against the same matrix (`tests/Vorcall.Server.Tests/PermissionEngineTests.cs`, and the ported `#[test]`s carrying the same names). The server is the boundary; the client mirror only hides and disables.
- Channel overrides resolve **sequentially by role position**: the `@everyone` override, then the member's other roles in ascending position order, then the member's own override, each as `(p & ~deny) | allow`. A higher role's override therefore wins a conflict. This is deliberately not Discord's union-of-allows rule.
- The registry's per-online-member `Visible` set is the audience of every channel frame: `BroadcastToChannel` sends to exactly those members. A member who gains sight of a channel gets `ChannelUpserted`; one who loses it gets `ChannelDeleted` addressed to it alone. Role, category and server deltas go to everyone regardless.
- `@here` is live-only: it notifies the members who are online but is never counted in `ReadState.mentions`. `@everyone` counts there like a direct mention.
- `RoleOrder` follows a `CreateRole`/`DeleteRole` that renumbered the other roles, not just a `ReorderRoles` — clients keep exact positions that way.
- `GET /api/images/{id}` answers a strong `ETag` of `"<id>"` (an image's bytes never change; a new picture is a new row), unlike an attachment's `"<id>-<size>"`.
- `assets/icons/*.svg` are **generated** by `assets/brand/gen.py icons assets/icons` and must come out byte-identical on a regeneration — edit the geometry in `gen.py`, never the SVGs. `client/crates/vorcall-app/src/brand/data.rs` is generated the same way (`uvx --with shapely python3 assets/brand/gen.py assets/brand`), and that mode does need shapely.
- Custom themes live as `themes/<slug>.json` beside `config.toml` in the platform config directory, selected by `config.theme = "custom:<slug>"`; the two presets are `"vorcall-dark"` and `"vorcall-light"`.
- `vorcall-hotkey` registers several bindings in one listener (push-to-talk, toggle mute, toggle deafen) and reports `(ActionId, Edge)`; `Binding` carries `ctrl`/`shift`/`alt`. The Wayland `GlobalShortcuts` portal is keyboard-only (no mouse buttons) and takes all the shortcuts in a single `bind_shortcuts` call; `WAYLAND_DISPLAY` set selects the portal backend, otherwise `DISPLAY` selects X11.
- **`dotnet build` output is localised (Portuguese) on this machine.** Grep for `Erro(s)`/`Aviso(s)`, or just read the exit code — `grep -i error` finds nothing in a failed build's output.
- `ClientConnection.cs` qualifies `System.Threading.Channels.Channel` in full, because the generated protobuf code now defines a `Channel` message too.
- `ConnectionRegistry.LoadAsync` throws on an unseeded database (no `server` row, no `@everyone`, no general channel). `Program.cs` boots in the order Migrate → `ServerDirectory.EnsureSeededAsync` → `ConnectionRegistry.LoadAsync`; never reorder those three.
- `AttachmentSweeper` runs two passes: unlinked attachments and unreferenced images, each once it is older than 1 hour. An image whose reference was replaced or cleared becomes unreferenced and is swept.
- The `uploads` rate-limit policy (`AttachmentsEndpoints.RateLimitPolicy`) covers `POST /api/images` as well as `POST /api/attachments`.
- nginx needs its own `location /api/images` beside `location /api/attachments` (raw body, `client_max_body_size 9m`, unbuffered) — a plain `/api/` proxy would apply nginx's 1 MiB default and buffer the whole upload.
- **A push to `main` deploys production immediately.** `.github/workflows/deploy.yml` builds and ships to `vorcall.example.com` on every push to `main`, with no separate approval gate. Do not push to `main` casually.
- **`client/.cargo/config.toml` only applies with cwd inside `client/`.** It supplies the placeholder `VORCALL_SERVER_KEY=dev` so a bare `cargo build` works there. Running cargo from the repo root does not pick it up.
- **Do not run the GUI binary (`vorcall`, `cargo run -p vorcall-app`).** It opens an iced window on the owner's desktop. Use `cargo build` / `cargo check` / `cargo clippy` to verify the client instead.
- **No `aws-lc-rs` in the client dependency graph.** Verify with `cargo tree -i aws-lc-rs` (from `client/`) — it must report no match. The Windows cross build (cargo-xwin) depends on `aws-lc-rs` staying out.
- The server Docker build context is the repository root, not `server/` — `server/Dockerfile` reads `proto/` via `COPY proto/ proto/`, and its `COPY` lines name the server csproj explicitly, so `tests/` never reaches the image.
- Never add `default_server` to `deploy/nginx/vorcall.conf` — that directive is already owned by another site on the production host.
- The client key and server URL are baked in at compile time (`VORCALL_SERVER_KEY`, `VORCALL_SERVER_URL`), overridable at runtime by env vars of the same names. A key rotation therefore requires a client rebuild and redistribution, not just a server-side change.
- `dotnet` may not be on `PATH`; it can live at `~/.dotnet/dotnet`. `dotnet-ef` needs `DOTNET_ROOT=~/.dotnet` and `dotnet` on `PATH`.
- ALSA headers are needed for any client build or clippy run on Linux — rodio/cpal won't compile without them (`alsa-lib-devel` on Fedora, `libasound2-dev` on Debian/Ubuntu).
- `Vorcall:JwtSigningKey` (env `Vorcall__JwtSigningKey`) is required; the server refuses to boot without it. `appsettings.Development.json` carries a dev-only value, so local runs need nothing extra.
- The CLI branch in `Program.cs` (`invites`/`users`/`server` as the first argument) never starts Kestrel — it runs migrations and exits. Don't expect the web server to come up under those subcommands.
- Never log tokens, passwords, invite codes, password hashes or the JWT signing key.
- Never run `dotnet build` from two agents at once — MSBuild has no target-dir lock, so concurrent builds of the same project corrupt each other's output.
- `dotnet ef migrations add` runs `Program.cs` at design time with empty `args`, so the CLI branch above must not trigger on an empty argument list; it also needs `ASPNETCORE_ENVIRONMENT=Development` so the required keys (`JwtSigningKey`, the dev `LogsDir`/`DiagnosticsDir`) load from `appsettings.Development.json`.
- Forwarded headers (`UseForwardedHeaders`) trust only the immediate hop (`ForwardLimit = 1`) because the backend is published on host loopback behind nginx, not reachable directly.
- `UseRateLimiter` runs after `UseAuthentication` in `Program.cs` on purpose: the upload rate-limit policy partitions on the bearer's user id, which `UseAuthentication` must have already resolved.
- The Hello sequence is `Welcome`, then one `ServerSnapshot` carrying the whole world the reader may see (server facts, every role, every category, the channels it may view with their overrides, its own DMs, every member as a `Profile`, the read states), then one `VoiceState` per voice or DM channel that has anybody in it, then `MemberUpdated{online = true}` to the other online members. There is no REST call after `Welcome` and no placeholder state to patch up afterwards.
- An attachment or image upload is a raw body, not protobuf, so nginx needs its own `location` for each (see above); the endpoints themselves already raise Kestrel's limit (`IHttpMaxRequestBodySizeFeature`).
- The attachment sweeper deletes an upload's row and file together once it has sat unlinked to any message for 1 hour; a client must send the `SendMessage` that references an attachment id well within that window.
- `Command`/`Event` in `connection.rs` derive `Debug` and carry attachment and image payloads as `Arc<Vec<u8>>` — never log one with `{:?}`, it dumps the raw image bytes.
- The client's image cache (`client/crates/vorcall-app/src/workers/images.rs`) lives under the platform cache directory, is pruned to 500 MiB at startup by oldest modification time, and all decoding happens off the UI thread.
- `MarkRead` is client-debounced to one call per second per channel, and only sent for the channel currently in view, scrolled to the bottom, in a focused window.
- The message list uses iced `Anchor::End`; under that anchor a relative offset of 0 means the bottom of the list, not the top.
- notify-rust's `show()` blocks on D-Bus on Linux — call it off the UI thread — and on macOS the notification is delivered when the returned handle is dropped, not when `show()` returns.
- rodio's `MixerDeviceSink` must stay alive in `App`; dropping it silences the mixer.
- The relay publishes UDP 5005 on `0.0.0.0` in production on purpose; nginx cannot proxy it; the OCI VCN security list is what actually gates it.
- `opus-rs` is a pure-Rust libopus port used in CELT-only mode; do not switch to hybrid/SILK modes (known decoder panics); decode is wrapped in a panic guard; the `[profile.dev.package.*] opt-level = 3` blocks keep debug builds from underrunning.
- `aec3` (pinned `=0.3.2`, pure Rust) is WebRTC's AEC3 + noise suppressor + AGC2 behind `vorcall-voice::cleanup`: 10 ms blocks (two per frame); `InputCleanup` is not `Send`, so the audio thread builds and drops it in place; AEC3 is always in the pipeline and is fed silence when echo cancellation is off; its metrics sink is a capacity-one, latest-only queue, pulled once per block.
- The cleanup chain runs on every captured frame before the gate and the meter, in both transmit modes and while muted (the canceller must stay converged); the voice worker guards it with `catch_unwind` like the codec and sends the raw frame for the rest of the session after a panic or error — toggling a switch or rejoining retries.
- The canceller's reference is what `VoiceSource` pulled from `Playout` (zeros while deafened), through a 200 ms ring shared with the audio thread; neither other applications' audio nor the notification chime (its own sink in `workers/audio.rs`) is ever cancelled.
- The cleanup unit tests use synthetic signals with thresholds taken from measurements (echo ≥ 12 dB removed at 100 and 250 ms with the delay estimate within 30 ms, white noise ≥ 6 dB, AGC lift 8–30 dB at −45 dBFS and ≤ 4 dB at −25 dBFS, everything off within 2.5 dB — each a floor under a measured value, never to be loosened); a pure tone is not speech to AGC2's VAD, so the gain tests use the speech-like generator, not `Tone`.
- Adding a `ServerFrame` payload requires arms in **both** dispatchers of `connection.rs` (`await_welcome` and `live_loop`), otherwise a known-but-unhandled payload reconnects the client.
- `VoiceReady.host` empty means the WebSocket host; the client uses `Endpoints::host()`.
- Never log `VoiceReady` frames or `MediaKey`/`VoiceSession.Key`; `connection.rs` logs frames through a redacting `describe()`, which is the **only** place a `ServerFrame` may be rendered for a log — it reduces `ChatMessage`/`MessageEdited` to id, channel, author id and text length. A debug-level file log (`vorcall.log`) always exists, so never log a frame with `{:?}`: it would put message text on disk.
- The audio thread (`workers/voice.rs`) owns cpal/rodio objects; never open devices on the UI thread.
- The macOS Input Monitoring grant for global push-to-talk is tied to the specific (ad-hoc signed) build, so it must be re-granted after every update; Caps Lock also cannot be a global PTT key there — it arrives as a modifier-flag change, not a key event.
- `Listener::start` in `vorcall-hotkey` blocks (up to 10 s on Wayland, waiting on the portal dialog), so the app always calls it via `spawn_blocking`, never on the UI thread.
- Hook and event-tap callbacks in `vorcall-hotkey` must stay trivial — the OS drops a slow hook (Windows) or tap (macOS).
- The voice-activation gate runs on every 20 ms frame in both transmit modes, because the input level meter depends on it; only voice-activation mode lets the gate force the talk-spurt marker.
- Per-peer volume/mute in `Playout` is keyed by ssrc; the app re-applies a user's saved setting whenever their ssrc changes (e.g. on rejoin). Priority ducking rides the same path: a 0.25 factor over every non-exempt peer's base gain while a priority speaker is speaking.
- Server mute and server deafen are moderator state, not local state: the client shows the two flags and refuses to let the user clear them.
- `client/.env.probe` (gitignored) holds the production probe credentials.
- `pkill -f vorcall-probe` from a shell whose own command line contains that string kills the shell; use `pkill -x vorcall-probe`.
- The repo is private, so friends' clients fetch updates from the backend (`/api/updates/*`, door key + bearer), never from GitHub Releases.
- The manifest signature covers the exact bytes of `manifest.json` — never re-serialise it. The server serves the stored bytes verbatim (`GetManifest` in `UpdatesEndpoints.cs`) and `vorcall-release sign` signs the file's bytes, not a re-encoded value.
- `client/update-keys.pub` empty ⇒ the updater is disabled (`disabled_reason` returns "no update keys baked in").
- The signing private key exists only in the GitHub secret `VORCALL_UPDATE_SIGNING_KEY` and the owner's password manager — never in the repo or on the host.
- Update crypto is ring-only (no `sha2`, no `ed25519-dalek`); `serde_json` is the only dependency the updater added to the workspace.
- Windows swap moves the running binary to `vorcall.exe.old` and relaunches into the new one; `.old` is deleted at the *next* start (the process exiting now may still be holding it).
- Unix swap renames the download over the running binary and execs it — safe because the kernel keeps the old inode alive for the process using it.
- The Linux release binary is built on the owner's machine by `scripts/push-client.sh`, not on a pinned CI runner, so the glibc floor is that machine's glibc (Fedora) — newer than the old `ubuntu-22.04` floor. A friend on an older distro can get a `GLIBC_2.xx not found` failure; building on an older base (container or VM) is the fix.
- First installs are the packages, never the bare binaries: `vorcall-linux-x86_64.tar.gz` (per-user `install.sh` into `~/.local`), `vorcall-windows-x86_64-setup.exe` (per-user into `%LocalAppData%\Programs\Vorcall` on purpose: Program Files would put the updater into its manual fallback) and `vorcall-macos-aarch64.dmg` (Finder opens a bare Mach-O download in TextEdit). The manifest lists only the three bare binaries, which the updater renames over whatever the package installed; of the packages only the Linux tarball reaches the host, and only because `scripts/push-client.sh` parks it there for the publish job to attach to the GitHub Release.
- `packaging/linux/vorcall.desktop` keeps that file name and `StartupWMClass=vorcall` because they match iced's `application_id`; that pairing is how the launcher gives the window its icon.
- `packaging/linux/install.sh` touches `~/.local/share/icons/hicolor` and rebuilds an `icon-theme.cache` that already sits there. GNOME re-reads a theme only when that directory's own mtime changes, and trusts an existing cache that is at least as new as the directory, so without both steps a cache left by another app hides the icon after a first install. It never creates a cache, which would lay the same trap for other installers.
- The macOS bundle's `Info.plist` must keep `NSMicrophoneUsageDescription`, or macOS kills the app on the first push-to-talk. `packaging/windows/vorcall.iss`'s `AppId` GUID must never change: it is how Windows recognises an upgrade.
- `VORCALL_NO_UPDATE` disables the updater at runtime; a dev-key build or a debug build never updates either.
- `VORCALL_RELAUNCHED=1` is set by the swapper on the process it just started; `vorcall-probe` prints a `{"relaunched": true, ...}` marker and exits when it sees it, which is what the oracle's swap case checks for.
- `users outdated` needs either `--min` or a manifest already on disk at `Vorcall:ReleasesDir` — with neither, it fails and says so.
- `min_version` lives in `client/Cargo.toml`'s `[workspace.metadata.vorcall]`, not next to `version` in `[workspace.package]`. For 0.5.0 it is `0.5.0`: a 0.4.x client knows nothing of channels and has to be cut off.
- `release.yml` refuses to publish unless the tag equals the workspace `version` (tag push, or dispatch with `publish` checked); a dry-run dispatch needs no tag.
- `release.yml` no longer compiles Linux or Windows: `scripts/push-client.sh` must have pushed `vorcall-linux-x86_64` and `vorcall-windows-x86_64.exe` (+ `.sha256`, + the tarball) into the host's `releases/<version>/` before the tag push, or the publish job fails at the fetch step; a dry run needs nothing on the host.
- nginx has a dedicated `location /api/updates/` (no buffering, 300 s timeouts — a release binary is a large streamed download) — applied to the host by re-running `deploy/provision-host.sh`.
- After a proto change, regenerate the smoke suite's pb2: `uvx --from grpcio-tools python -m grpc_tools.protoc -I proto --python_out=$HOME/.cache/vorcall-smoke proto/vorcall.proto`.
- `MediaHeader.MaxDatagram`/`MAX_DATAGRAM` (1200 bytes) is defined independently in exactly two places that must move together: `client/crates/vorcall-voice/src/packet.rs` and `server/Voice/MediaHeader.cs`; `crypto.rs` and `engine.rs` only import `packet::MAX_DATAGRAM` for their bound checks.
- The replay window (`ReplayWindow.Size`, `server/Voice/ReplayWindow.cs`) is 1024 sequence numbers, not the smaller window a voice-only relay would need — a screen share sends far more packets per second than voice and shares voice's one sequence counter.
- Video and share-audio packets (types 4 and 5) are charged to a per-session byte budget (`Vorcall:ShareMaxKbps`, `VoiceSession.ShareBucket`), never to the packet-rate bucket that governs audio, pings and keyframe requests.
- `FrameSender::send_video` (`vorcall-voice/src/engine.rs`) paces itself with a blocking sleep every `VIDEO_BURST` (8) fragments, and retries a fragment the socket refuses transiently (`WouldBlock`, or `ENOBUFS` — what macOS answers a full interface queue with) up to 40 × 1 ms before counting it in `Stats.send_failures` and abandoning the rest of that unit — call it from a worker thread, never the UI or audio thread.
- Every packet type — audio, video, share audio, keyframe requests — draws from the same one `seq` counter per session (`Shared::seq`); there is no per-stream counter.
- `Speaking` is derived from type 1 (audio) alone; share media, video included, never marks a session as speaking, and a server-muted session's audio is dropped before it could.
- `Playout`'s output is stereo; the far-end reference for the two echo cancellers is the mono downmix `(l + r) / 2` of every played frame, pushed into two separate rings — one for `InputCleanup` (the microphone), one for `ShareCleanup` (loopback share audio) — both owned by the audio thread.
- `ShareCleanup` (`vorcall-voice/src/cleanup.rs`) is not `Send`, like `InputCleanup`; it is built and dropped in place on whichever thread runs it (the share pipeline thread, not the audio thread).
- OpenH264's `num_threads` alone does nothing — it sets `iMultipleThreadIdc` but leaves the slice layout at one slice, so multi-threaded encoding goes through the raw API (`Encoder::raw_api`, `SEncParamExt`, `SM_FIXEDSLCNUM_SLICE`) in `vorcall-screen/src/codec.rs`; frame skipping (`skip_frames(true)`) must stay on through any change there — a screen share's byte budget depends on the encoder skipping whole frames rather than the relay cutting one in half.
- `openh264-sys2` is a direct dependency of `vorcall-screen` only for the raw parameter struct and option ids the threaded encoder needs — `openh264` (the safe wrapper) is what actually builds and drives the encoder.
- `[profile.dev.package.openh264-sys2] opt-level = 3` in `client/Cargo.toml`: `cc-rs` compiles OpenH264 at the package's own opt level, and a `-O0` build of it cannot keep up with one frame in a debug build.
- Windows Desktop Duplication frames exclude the cursor entirely; `vorcall-screen`'s Windows backend composites it back in from the separately-queried pointer shape. Windows.Graphics.Capture draws its own yellow border around a captured window for an unpackaged app regardless of `SetIsBorderRequired(false)` (only honoured on newer Windows builds, and even then only for a packaged app).
- macOS screen capture needs macOS 13 (`LSMinimumSystemVersion` in the bundle's `Info.plist`); the Screen Recording grant, like Input Monitoring, is tied to the specific ad-hoc-signed build and must be re-granted after every update, taking effect only after a relaunch.
- Every share on Linux raises the desktop portal's own picker: no restore token is kept and `PersistMode::DoNot` (`ashpd::desktop::screencast`) asks the portal to persist nothing. A remembered source would let a later share broadcast a window the user has forgotten was chosen, which is worth one dialog per share.
- `vorcall-screen`'s Linux backend links `libpipewire-0.3.so.0` at build time (pkg-config + bindgen, needing `libclang`) and at run time — unlike the Wayland portal in `vorcall-hotkey`, this is a hard link, not a soft dependency, so a missing PipeWire keeps the whole client from starting, not just screen sharing; `packaging/linux/install.sh` only warns, it does not fail the install.
- On the Linux capture thread every ashpd/zbus object (the `Session`, the `Screencast` proxy, the `Closed` signal stream) must be dropped inside the tokio runtime context — zbus 5 spawns its match-rule cleanup from `Drop`, and a drop outside the context panics in a destructor and aborts the whole app (the 0.4.0 crash on stopping a share). `linux/mod.rs` holds a `runtime.enter()` guard for the thread's life and orders the drops explicitly; `vorcall-probe --capture-seconds` is the oracle.
- The stage's `wgpu::Pipeline` (`StagePipeline` in `view/stage.rs`) is one instance per renderer engine; since the popped-out stage window has its own renderer, it holds its own set of Y/U/V textures, uploaded independently of the main window's.
- iced's software (tiny-skia) renderer fallback cannot draw a `shader` widget at all — the stage renders nothing under it, same as any other shader-based iced widget.
- `deploy/provision-host.sh`'s sysctl step (`/etc/sysctl.d/90-vorcall.conf`, `net.core.rmem_max`/`wmem_max` = 16 MiB) has to run before the relay's 8 MiB socket buffers can actually take; without it the kernel clamps them to the old default silently, no error either side.
- `Vorcall:ShareEnabled` is the server-side kill switch for screen sharing; voice keeps working with it off, every `StartShare` just answers `ERROR_CODE_SHARE_UNAVAILABLE`.
- Serilog is configured only in `Program.cs` (`LoggingSetup.Configure`, `UseSerilogRequestLogging`) and `server/Logging/`, never in `ServiceSetup` — the admin CLI (`AdminCli.RunAsync`) keeps the default console provider and must never open the log file the running server is writing to. Levels live under `Serilog:MinimumLevel` in `appsettings*.json`; the old `Logging` section is gone — adding one back changes nothing.
- The test project lives under `tests/`, not `server/`, because a project under `server/` would be glob-compiled into the server csproj. `Program.cs` ends with `public partial class Program { }` so `WebApplicationFactory<Program>` can find it — keep it.
- `Microsoft.EntityFrameworkCore.Relational` is referenced explicitly in `server/Vorcall.Server.csproj` at the same version as `Microsoft.EntityFrameworkCore.Design`: Design is `PrivateAssets="all"`, so the EF Core version it lifts the server to never reaches `tests/Vorcall.Server.Tests`, which would otherwise resolve Npgsql's lower floor and fail with CS1705. Bump both together.
- `/metrics` counts channels, not rooms (`vorcall_channels`), and the relay's drop reasons now include `muted` and `channel_gone` (not `room_gone`); its per-30 s log line is per channel.
- `/metrics` and `/api/admin/*` refuse a non-private source (`PrivateSource.IsPrivate`: loopback, RFC 1918, link-local and their IPv6 counterparts; a null peer is the in-process test host) with the same 404 as an unknown path, and nginx answers 404 for both itself. `/metrics` is outside `/api` on purpose, so the door-key middleware does not gate it.
- The rate-limit windows (`Vorcall:AuthRequestsPerWindow`, `UploadRequestsPerWindow`, `DiagnosticsReportsPerHour`, `MessageBurst`/`MessagesPerSecond`) are configuration so the test host can raise them — the fixture sets them to 100000.
- `users disable`/`users enable` (the admin CLI's account lock, renamed from `users ban`/`users unban` so nothing reads as the in-app ban) need the admin endpoint only for the live kick — `users.disabled_at` and the token revocation hold regardless, and the bearer check picks the lock up within `DisabledAccounts.Ttl` (30 s). Without `Vorcall:AdminKey` the admin endpoints are not mapped and the CLI prints "admin endpoints are off". An open socket is also closed with 4003 "account disabled" at its next write frame — `ChatSocketHandler` asks `DisabledAccounts` before charging the write limiter — so the kick only shortens the wait. A **ban** is a different thing entirely: `BanMember` over the socket writes a `bans` row, tombstones every message of the target, drops its overrides and removes it from the server.
- `docker compose run --rm backend …` is a sibling container, so it needs `Vorcall__AdminUrl=http://backend:5000` (in the host's `.env`) to reach the live server for `users kick`/`disable`/`enable`; the default `http://localhost:5000` is for local dev.
- Close codes 4001 ("kicked by admin") and 4003 ("account disabled", what a `users disable` sends — a lock, never a ban) are terminal for the client's reconnect loop (`DisconnectReason::Kicked`/`Disabled` in `connection.rs`, beside the `Banned` that a fatal `ERROR_CODE_BANNED` frame carries): it signs out and returns to sign-in instead of backing off.
- The nightly backup cron is `/etc/cron.d/vorcall-backup` (03:15 UTC, `/usr/local/bin/vorcall-backup-db`, 14 days kept); the restore recipe is the header of `deploy/backup-db.sh` and README § Production — it is destructive (`pg_restore --clean`), stop the backend first.
- The client's log directory is the config directory (`config::log_dir()`, `ProjectDirs::from("br.com","freedomit","vorcall").config_dir()`): `vorcall.log` rotates at 5 MiB keeping `.1`–`.3`, `crash-<utc>.txt` keeps the last 5; `RUST_LOG_FILE` filters the file, `RUST_LOG` the console (stderr). `diagnostics::init("info")` and `install_panic_hook` run in `vorcall-app`'s `main` right after the `--version` exit and the swap cleanup, before iced starts; `vorcall-probe` keeps a plain stderr subscriber and writes no file.
- On macOS the block buffer `CMSampleBufferGetAudioBufferListWithRetainedBlockBuffer` hands out carries one retain that is the caller's to release (the Create rule); the audio-buffer-list data pointers point into it, so `macos/stream.rs` holds it in a `CFRetained` until the samples are copied out and releases it exactly once by the drop — never earlier, never leaked. Audio samples arrive on their own dispatch queue, separate from video's.
- `POST /api/diagnostics` is capped per file at 4 MiB (`DiagnosticsOptions.MaxFileBytes`); the client trims each file to its last 4 MiB before uploading (`report::tail`), so a 5 MiB `vorcall.log` still goes through. The default `DiagnosticsReportsPerHour` is 10 because one report is up to two log files plus five crash reports, each its own request; the client deletes a crash file right after its own upload succeeds.

## Conventions

- English only — code, comments, docs, commits.
- Conventional Commits (`feat:`, `fix:`, `chore:`, ...).
- Comments only where the "why" is non-obvious (an external constraint, a spec citation, a workaround's cause) — not restating what the code already shows.
- No new dependencies without discussion first.
- Never hand-edit generated protobuf code. To change the schema, edit `proto/vorcall.proto` and rebuild both sides (`cargo build` in `client/`, `dotnet build` in `server/`) so the generated code regenerates.
